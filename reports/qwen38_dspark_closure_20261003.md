# DSpark 高并发边界、贪心分歧与缓存准入补充验证

2026-10-03，4×NVIDIA A30、物理 GPU 1/5/6/7、TP4。目标 Qwen3.8-27B BF16，匹配 DSpark 草稿；模型、运行时与输入的版本约束沿用[首次实验](qwen38_dspark_tp4_20261003.md)。所有自建 GPU 服务已经退出。

仓库迁移说明：压缩原始记录、四份汇总与校验清单位于 `results/qwen38_multigpu_20261003`。使用 `benchmark/qwen38_multigpu/reproduce_results.py` 可无需 GPU 重新计算这些结果；解压时仅迁移文件路径引用，JSONL 内容、容量窗口偏移及测量值保持不变。

## 结论

- 并发 16，优化方案相对自回归的吞吐为 **0.995×**，五轮范围 **0.974×–1.016×**：基本持平，没有稳定吞吐加速。在这项负载、缓存预算下，吞吐优先时建议使用自回归；没有实现或验证自动回退功能。
- 序列并不逐 token 相同。独立诊断核查 **13,056 个**实际输出 token，均符合各自执行路径的目标 argmax；所查首分歧对应相同前缀下 BF16 目标 logits 排序变化。普通自回归的串行/并发对照也复现了这类变化，不能把它直接等同于草稿错误接受。
- 同为每卡 4.5 GiB 缓存预算，AR 的 GDN 组每请求申请 1 块，DSpark 申请 8 块。DSpark 记录到需要 95 块、仅剩 88 块而推迟准入，95 块中 80 块属于 GDN 状态。这证明本次状态容量限制确实造成请求排队，不证明全部端到端回退都由它造成。

## 五轮直接对照

新实验固定同一组约 2K 输入、256 个实际输出 token、16 个请求、客户端并发 16；关闭 thinking/prefix cache，greedy、忽略 EOS 以固定性能输出预算。每卡缓存预算 4.5 GiB、max-num-seqs=32、max-num-batched-tokens=2048，沿用已冻结预算映射 `1→7、3→4、11→4`，没有用这些结果重新拟合策略。

每轮分别启动 AR 与 DSpark 引擎，随机打乱引擎顺序；DSpark 引擎内随机比较原始验证/原始图桶、仅细分图桶、预算+细分图桶，共享同一个 45 图池。native 指原始验证及原始图桶策略，承担共同图池的资源成本；不要把它视作与首次独立新进程原生 DSpark 完全相同的部署条件。预热后计时，排除模型加载、捕获和独立诊断。这里仍是有限请求组，不是稳态线上 QPS。

| 比较 | 五轮配对吞吐比中位数 | 五轮范围 |
| --- | --- | --- |
| 原始策略 / AR | 0.931× | 0.766–0.951× |
| 仅细分图桶 / AR | 0.927× | 0.870–0.978× |
| 预算+图桶 / AR | **0.995×** | **0.974–1.016×** |
| 仅细分图桶 / 原始策略 | **+0.9%** | -5.1% 至 +17.9% |
| 预算+图桶 / 仅细分图桶 | **+8.2%** | +1.7% 至 +11.9% |
| 预算+图桶 / 原始策略 | **+7.8%** | +4.7% 至 +27.8% |

统计使用同轮比值的中位数。单轮严格满足 `budget/AR = (budget/native) × (native/AR)`，但**两个比值的中位数相乘通常不等于乘积的中位数**。首次实验的 0.898× 与 1.057× 还来自不同引擎/图池对照，约 0.95× 只能是粗估，本次 0.995× 是直接测量。

并发 16 的原始策略有一轮明显慢于其余轮次，保留在原始数据和上述范围内，没有因数值不好而删除。优化方案五轮有三轮低于 AR、两轮高于 AR；不能表述为每轮没有翻正，也不能表述为稳定高于 AR。

优化方案的客户端 TPOT 相对 AR 降低约 **40.6%**（同轮比值中位数），吞吐却基本持平，说明活跃请求输出间隔和整个含排队请求组的完成速度是不同指标。吞吐优先的策略建议不等于所有延迟 SLO 都应选择 AR。

新消融中目标图的捕获 token / 有效 token 比仍为：原始桶 **1.413**、细分桶 **1.094**、预算+细分桶 **1.103**。1.41→1.09 属于图桶消融；组合方案约 1.10。这是形状计数，不是 FLOPs 或 GPU 时间降幅。

图桶和预算收益是逐级消融：预算的 +8.2% 以完成图适配的版本为基线，不是未经图适配的独立预算收益。首次混合并发消融记录的 +3.2%、+1.6%、总 +5.7% 保留为历史结果；最新简历的并发 16 数字使用本次直接对照。并发 4 的 +6.3% 仍来自首次五轮 held-out 消融。

数据：`outputs/qwen38-evidence/threeway-resumed.json` 及 `.summary.json`，`complete=true`，20 组有效测量，HTTP 错误为零。旧的 `threeway-final.json` 在第 9 组后因清理检查的利用率读数未归零而中断；恢复文件保存原失败、SHA-256 与源码哈希，复用有效组并补齐剩余条件。空闲检查同时核对显存和真实计算进程，保留利用率快照。

## GDN 占用与排队的实际证据

独立 AR/原生 DSpark 容量探针使用同一组 16 个提示词，固定 128 输出、相同 4.5 GiB/卡预算，记录真实缓存管理器的分组需求及 `allocate_slots` 返回值。没有更改分配结果，也没有用开启探针时的吞吐作为性能结论。

| 项目 | AR | DSpark |
| --- | --- | --- |
| GDN 缓存组数 | 3（各 16 层） | 10（各 4/5 层） |
| 每组每请求首次状态申请 | 1 块 | 8 块 |
| GDN `num_speculative_blocks` | 0 | 7 |
| 16 请求窗口分配暂缓次数 | 0 | 34 |
| 发生暂缓的不同请求数 | 0 | 3 |

草稿引入的缓存类型与层数改变了分组布局，AR/DSpark 的全局池分别为 376/1,134 块，页尺寸及每块覆盖的层数也不同。**不能直接比较两个全局块数或总申请块数来推导字节容量倍数**；可靠比较是各组的状态检查点数、同一池内的需求/空闲、以及字节预算本身。

一次真实暂缓记录是：`running=11、waiting=5、required=95、free=88、watermark=0`，其中 10 个 GDN 组各需要 8 块（共 80），4 个目标 FullAttention 组各 3 块（共 12），草稿 SlidingWindow 组需要 3 块。分配返回 `None`，请求留在等待队列，最终所有请求正常完成。34 次是重复尝试，不是 34 个请求报错。

这确认了状态容量引发的准入限制，仍没有隔离状态保存/回滚的 GPU 时间，也没有给各瓶颈分配端到端回退百分比。本项目预算适配依然按最大 K=7 配置状态池，缩短实际验证前缀不会把 8 个状态块改成 5 个，因此没有消除这一容量约束。

数据：`capacity-final.json`、`.ar.jsonl`、`.fixed.jsonl` 与 `.summary.json`；`complete=true`。探针包装原有缓存协调器/各组管理器，只观察原调用的返回值，没有重复执行分配计算或更改状态需求。

## 贪心决策与序列分歧

在性能行之外独立采集目标 logits 的 top-8、argmax、实际采样输出、请求位置和执行形状；恢复采样函数后退出引擎。关联实际 HTTP token IDs，检查四个 TP rank 一致，重复的四卡记录只计一次。

第一次诊断：AR/原始 DSpark/预算方案各 18 次请求、128 输出，合计 **6,912** 个输出决策。追加容量诊断：AR 的并发及串行各 16 请求、DSpark 的并发 16 请求，合计 **6,144** 个决策。总 **13,056/13,056** 符合各自目标 argmax，不能将这个比例解释成“与 AR 的生成序列逐 token 一致率”。这些请求包含重复提示词和执行条件，不是 102 个独立质量任务。

在第一次并发 16 诊断中，AR/原始策略完整 128-token 序列相同 4/16，AR/预算相同 6/16，原始/预算相同 3/16。相同前缀的首分歧都对应目标 argmax 改变；top logits 的共享项变化为 0.125 或 0.25，常伴随最高分平局。两边都输出了各自的目标 argmax，未观察到违反本路径贪心目标的接受决策。

一个例子：相同 1,801-token 提示词及前 7 个生成 token，下一个候选 57358/29854 的 AR 分数为 **20.875/20.750**，DSpark 为 **20.875/20.875**。AR 选择 57358，DSpark 在平局下选择较小 ID 29854；原始 argmax 与实际输出都匹配。这里 logits 的实际 dtype 为 BF16，20 附近的 BF16 分辨率为 0.125。定位的是首个贪心分歧的打分与排序原因，不是已定位某个唯一 CUDA kernel 的误差来源。

普通 AR 的额外串行/并发对照中，完整序列相同 **7/16**，另外 9 条也在相同前缀下出现目标 logits 排序变化，且实际输出符合目标 argmax。这在没有草稿模型的路径也复现了执行形状相关的数值差异。单请求重复诊断的三个模式各为 1/1 序列相同，范围很小，不能据此宣布所有执行形状确定。

新增 AR/原生 DSpark 的固定 16 短任务、自然 EOS 和 newline/END 两项 stop 全部通过；预算版本相同检查已在首次 `budget-v2.json` 中通过。短任务结果、argmax 决策检查和分布无损证明属于不同层次。没有证明所有输入的分布完全相同，没有保证所有贪心长序列一致，未逐层隔离数值误差。

背景参考：[vLLM 投机解码文档](https://docs.vllm.ai/en/latest/features/speculative_decoding/)、[vLLM 可复现性说明](https://docs.vllm.ai/en/latest/usage/reproducibility/)。官方说明区分算法层面的无损性与批次/数值稳定性；本项目结论以本机固定版本及上述实际诊断为准。
