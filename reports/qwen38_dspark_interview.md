# 这个项目怎么讲

## 先讲最新完成的实验

> 我在四张 A30 上，用 TP4 部署了 Qwen3.8-27B BF16 和匹配的 DSpark 草稿。为了确认投机解码实际能省多少时间，我固定同一批约 2K 输入、256 输出、每卡 4.5 GiB 缓存预算，对普通解码和原生 DSpark 做了五轮配对测试。并发 1 的吞吐是基线的 2.43 倍，并发 4 是 1.69 倍，但并发 16 降到 0.90 倍。高并发接受长度更长，所以问题不能只用接受率解释；我继续检查运行与等待请求，以及验证阶段的额外状态和图补齐。

以上加速是原生算法接入与评测的结果。个人图分档、统一验证前缀的额外收益，须用独立消融结果说明，不能把整个 2.43 倍说成自己实现的新算法收益。

> 我的具体改动是在异步调度里按活跃 batch 选择统一验证前缀，并为不同 query 宽度和请求桶适配 CUDA Graph。先校准再冻结，换提示词做五轮消融；并发 4 相对同引擎原始策略提升 6.3%。并发 16 我又补了五轮直接比较 AR、原始策略、图分档和组合方案：组合方案较原始策略提升 7.8%，但相对 AR 只有 0.995 倍，基本持平，没有稳定吞吐加速。在这项固定缓存预算下，吞吐优先时我建议使用 AR；低并发才是明确收益区间。

并发 16 的新直接对照取代旧的两个独立比例估算，具体条件见[补充报告](qwen38_dspark_closure_20261003.md)。新实验的 DSpark 三组共用扩展图池，因此“原始策略”指原始验证预算与原始图桶，不是完全独立的原生部署。五轮组合方案/AR 为 0.974–1.016×，三轮低于 AR、两轮高于 AR；客户端 TPOT 仍降低约 40.6%，所以吞吐与输出间隔要分开讲。

## 被问到两个改动各贡献多少

> 我做的是逐级消融。先保持完整验证 K=7，只细分图桶，padding 比从 1.41 降到 1.09，但吞吐配对中位数只提升 0.9%，收益不稳定。再在细分图桶上开启冻结的验证预算，增加 8.2%；组合方案相对原始策略增加 7.8%。预算的 8.2% 是以图适配后的版本为基线，不是预算独立收益。

以上为并发 16 的新五轮直接对照。配对比值的中位数不具备乘法可分性，不能相加或相乘这些中位数来重建最终比例。仍未做完整 2×2 因子实验；没有测出图与预算的独立交互项。组合方案的 padding 比约 1.10，而 1.09 属于仅图桶消融。

## 被问到是不是无损、为什么序列不同

> 我没有把小任务答案一致当成无损证明。核查了 13,056 个真实输出 token，全部符合各自执行路径的目标 argmax。但 AR 和 DSpark 的完整贪心序列并不相同；在相同前缀的首分歧处，两条路径的 BF16 目标 logits 出现 0.125 或 0.25 的变化，导致最高分排序或平局变化。AR 自身换串行/并发也复现了这类差异，所以不能直接说成草稿被错误接受。

这些是包含重复提示词的固定诊断，不是 13,056 个独立质量样本。AR 的额外串行/并发对照只有 7/16 条完整序列相同；首次 AR/原始 DSpark 并发诊断为 4/16，AR/预算为 6/16。定位到了首个决策的 logits 排序原因，尚未隔离唯一的 CUDA kernel 或证明全输入分布无损。16 个短任务及 EOS/stop 回归另行通过。

## 算法一轮做了什么

普通自回归解码每步由目标模型产生一个 token。DSpark 草稿以并行 backbone 产生多个位置的 hidden states，再用顺序 Markov head 提出候选；目标模型一次验证一段候选，接受连续正确的前缀并产生 bonus token。草稿不是我训练的，拒绝采样也来自 vLLM。

本地权重明确 `sample_from_anchor=true`，草稿固定 7 个 query；目标验证 K 个候选时是 K+1 个 query。因此草稿 width=7，完整目标验证 width=8，缩短验证前缀后目标 width=2/3/5。不能只看到权重是 speculators 格式就假定采用某种 query 布局。

## 怎样发现高并发的损失

先观察症状：并发 16 平均接受长度约 3.32，高于低并发约 2.93，但整个请求组吞吐没有提升。HTTP TPOT 仍下降约 27%，说明已运行请求的输出间隔改善，不能据此断言排队中的请求也更快。

再看准入：原生 DSpark 的测量日志记录过 `Running=8, Waiting=8` 和 `Running=10, Waiting=4`。这不是 GPU batch 恒定为 8/10 的证明，但确认了准入排队。HTTP 并发 16 与实际驻留 GPU batch 不是一回事。

先从代码算状态量级：目标有 48 层 GDN，TP4 下每卡 12 个 value heads，每层 FP32 recurrent state 为 `12×128×128×4=0.75 MiB`；合计一个检查点约 36 MiB/请求/卡。7-token 验证配置需 8 个状态块，约 288 MiB/请求/卡，仅这一部分 16 请求就达到 4.5 GiB。这是配置推导，不是直接测量，也未包含 attention KV、卷积状态和 padding。

然后补实际分配探针：在相同 4.5 GiB/卡预算下，AR 的 GDN 组每请求首次申请 1 块，DSpark 为 8 块。DSpark 的 16 请求诊断记录到 34 次分配暂缓、涉及 3 个不同请求，AR 为零。一次暂缓时运行 11、等待 5，需要 95 块、只有 88 块，需求中 80 块是 GDN；原始分配返回 None，因此推迟准入。这证明状态容量限制造成了实际排队，但没有给全部吞吐回退分配原因百分比。AR 与 DSpark 分组、页大小不同，不能把全局块数直接当成字节容量比较。

最后才用单独的 Nsight trace 检查 target、draft 和通信 kernel 的构成。NCCL kernel 时长包含设备等待，不能全说成线上传输时间；累计 kernel 占比也不是请求延迟占比。

## 我具体写了什么

- 在异步调度器中用新的列表切片限制验证前缀，避免原地修改共享 placeholder；草稿仍产生完整 block，保留原生拒绝采样和状态管理。
- 根据真实活跃 batch 在 K=1/2/4/7 间校准，超过完整验证 3% 才采用，冻结映射后换未参与校准的提示词测试。
- 为目标不同 query width 和草稿固定 query width 捕获 CUDA Graph，增加 6/12/24 请求桶。例如 10 请求可以补齐到 12，原始桶补齐到 16。
- 在同一引擎和图池内拆分“原始桶”“细分桶”“细分桶+预算”三组。图补齐减少和验证预算效果单独统计；自己复用的上游接口也要说明。

CPU 图分派检查覆盖 224 个组合。GPU 接入确认每个 rank 捕获 36 张目标图和 9 张草稿图。最终性能和质量以报告中完成的结果文件为准。

## 哪些话不能说

- 没有实测 TP8，也未验证这个 20 Q-head 草稿的默认 TP8 切分。
- 并发 1–16 并非都加速；低并发和高并发的边界要讲清楚。
- 长序列 greedy 输出已经观察到差异，不能说逐 token 一致或普遍无损。目标 argmax 诊断定位了首分歧的数值排序变化，没有证明所有输入的分布一致。
- 当前统一预算实现不会缩小按 K=7 分配的最大状态容量，因此不能说它解决了显存容量问题。
- 没有测得显存带宽饱和，没有训练草稿，也没有新写 CUDA 算子。

最新直接对照、贪心决策及容量证据见[补充报告](qwen38_dspark_closure_20261003.md)；低并发结果与 Nsight 证据见[首次实验报告](qwen38_dspark_tp4_20261003.md)。
